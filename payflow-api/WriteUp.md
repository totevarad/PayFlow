## Task 3: Repository Layer
**SQL Generated for `findByUpiId`:**
```sql
select u1_0.user_id, u1_0.balance, u1_0.name, u1_0.phone_number, u1_0.upi_id 
from "USER" u1_0 
where u1_0.upi_id=?
```
**Explanation:**
- **(a) How JPA derives it:** Spring Data JPA parses the method name `findByUpiId`. It strips the `findBy` prefix to determine the intention (a SELECT query), and takes `UpiId` to map it to the `upiId` field (column `upi_id`) in the `User` entity to use in the `WHERE` clause.
- **(b) What the `?` means:** The `?` is a parameter placeholder used in Prepared Statements. It prevents SQL injection by treating the input as literal data rather than executable code when the database executes the query.

## Task 6: Custom Query Comparison
1. **Derived method names (`findBy...`)**: Simplest to write, Spring writes the query for you based on naming conventions. Good for straightforward queries but becomes unwieldy for complex logic (e.g. `findByNameAndBalanceGreaterThanOrAgeLessThan`).
2. **`@Query` (JPQL)**: You write an object-oriented query string targeting your Java Entity classes and fields, not the database tables. It gives you more power while maintaining database portability.
3. **Native SQL**: You write raw SQL targeting the exact database (e.g., specific H2 syntax). 
**Why native queries are least preferred:** They lock your application to a specific database vendor. If you switch from H2 to PostgreSQL or MySQL, your native SQL queries might break due to syntax differences, whereas JPQL and derived methods are automatically translated by Hibernate to match the target database dialect.

## Conceptual Write-Up (Section 4)

1. **Request lifecycle:** 
When curl sends `POST /users`, the embedded Tomcat server receives the HTTP request and routes it to Spring's **Dispatcher Servlet**. The Dispatcher Servlet consults the Handler Mapping to find the correct controller method, identifying `UserController.registerUser`. The **Handler Adapter** then processes the request, invoking Jackson to deserialize the JSON body into a Java `User` object, and finally executes the method.

2. **Serialisation:**
The Jackson library (specifically `MappingJackson2HttpMessageConverter` in Spring) automatically converts the incoming JSON payload into the Java `User` object using reflection. If the JSON key is `"upi_id"` instead of `"upiId"`, Jackson won't be able to map it automatically (since it looks for exact name matches or standard getters/setters), leaving the `upiId` field in the Java object as `null`.

3. **Spring Boot features:**
   - **Embedded Server**: PayFlow runs on an embedded Tomcat server directly from the `main` method. We don't have to install or deploy a `.war` file to an external web server.
   - **Auto-Configuration**: Spring Data JPA and the H2 database were configured automatically just by having them on the classpath, saving us from writing verbose `DataSource` and `EntityManager` configuration files.
   - **Production-Ready Defaults**: Features like Jackson for JSON conversion and HikariCP for connection pooling are pre-configured. This allowed our REST endpoints to instantly parse JSON without additional setup.

4. **Spring vs. Spring Boot:**
If we used plain Spring, we would have had to manually configure a web server, write complex XML or Java configuration files to set up the `DispatcherServlet`, configure the database connection (`DataSource`), and explicitly configure the transaction manager and JPA factory. Spring Boot takes care of all this boilerplate automatically via convention-over-configuration.

5. **Stateless REST:**
Stateless means the server doesn't store any client session data between requests—each request contains all the information needed to process it independently. This matters for load balancers because consecutive requests from the same client can be routed to any of the three servers without breaking the application logic, as no server relies on stored state from previous requests.

6. **Persistence:**
If we had stored transactions in a Java `List` (in-memory variable), all transaction records would be permanently erased when the server restarts or crashes. For a payments app, this is unacceptable because financial data must be durable and reliably stored on disk (persisted) to maintain accurate user balances and audit trails across restarts.
